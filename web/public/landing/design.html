How Runko is designed

Runko is a bet that the shape of source control has to change now that most code is written by machines. This page is the argument: what Runko is, where the GitHub model breaks, and why we think this is the direction the industry moves in.

What it isA monorepo operating system, layered on Git.

All your code lives in one Git repository — and Runko is the layer that makes that pleasant instead of punishing. It runs on your own infrastructure, it is open source under Apache-2.0, and it is aimed at teams of roughly twenty to three hundred engineers plus however many agents they point at the codebase.

Three things define it. The repo describes itself: which projects exist, who owns which paths, what depends on what, and which checks must pass are all small files in the tree — versioned and reviewed like any other code, never clicked into a settings page. The unit of work is a Change, not a branch: every change carries a stable identity that survives rebasing and amending, so review state, approvals and check results follow it as it moves. Every agent gets a real workspace: a server-tracked checkout of just the slice it needs, that you can watch live, take over, and constrain from the server side.

What Runko deliberately is not: a new storage engine, a virtual filesystem, or a CI runner fleet. It is plain Git underneath — you can clone it with git, and it mirrors out to GitHub so nothing you already own stops working.

Why not just GitHubThe old model assumed the expensive thing was writing the code.

GitHub is excellent at what it was designed for: humans, pushing branches, opening pull requests, reviewing each other's work at human pace. Almost every part of that design assumes changes are scarce and review capacity is abundant. Once a fleet of agents is authoring, both assumptions invert — and the cracks are structural, not cosmetic.

Code split across many repositories

The old model

An agent can only see the repo you handed it. Cross-cutting work becomes a chain of PRs across repos, merged in the right order, with version bumps in between — and the agent silently misses the callers it was never shown.

Runko

One repository, so a change that touches four projects is one atomic commit that reviews and lands together. Every agent gets a complete, consistent view of the code — no coordination protocol to get wrong.

Branches and pull requests as the unit of work

The old model

A PR is pinned to a branch. Rebase it and review context frays; stack dependent work and you are hand-managing a tower of PRs that all need re-targeting whenever the bottom one changes.

Runko

Changes carry a stable identity across amends and rebases, so a stack is a first-class thing: rework the bottom, everything above follows, one push updates the whole series, and they land bottom-up on their own.

Guardrails that live in the prompt

The old model

An agent runs with a human's credential and that human's full write access. The only thing stopping it from editing the deploy config or approving its own work is instructions in a prompt — which is to say, nothing enforceable.

Runko

Agents are real principals with their own identity and stricter defaults, enforced by the server: which paths they may touch, how large a change may be, no self-approval, no approving at all. A prompt injection cannot argue its way past a rejected push.

CI that re-runs the world

The old model

Either everything runs on every PR, or someone hand-maintains path filters that quietly rot. Multiply that by ten agents opening changes all day and CI becomes the bottleneck, the bill, and the reason people stop trusting a red build.

Runko

Runko computes exactly which projects a change affects from ownership and declared dependencies in the tree, and requires only those checks. A green change whose rebase applies cleanly lands without re-running anything.

Work that only exists on someone's laptop

The old model

An agent's work-in-progress lives in an uncommitted working directory. The session dies, the container is reaped, and the work is simply gone — and while it ran, nobody could see what it was doing.

Runko

Workspaces are tracked by the server and snapshot as the agent works. Nothing is lost when a session dies, you can watch ten agents at once on one page, and you can pick up any of their workspaces yourself.

The pillarsFour commitments every feature follows from.

01One monorepo that feels small.

All your code lives in one Git repository, but nobody has to carry all of it. You check out just your slice — the rest stays on the server until you need it. Projects and ownership are small files in the tree, so the repo describes itself.

02Trunk-based development, enforced.

There is one branch that matters, and nobody pushes to it directly — not even admins. Every change goes through the same gate: owner approval, required checks, a secret scan. If trunk moved while you waited, Runko only re-runs the checks your change could actually have broken.

03Agents work in parallel, safely.

Run several coding agents on the same repo at once. One command gives each its own workspace — a checkout of just its slice, all sharing one clone underneath — no git worktree juggling. Work-in-progress snapshots to the server as it goes, so a killed agent loses nothing. And the server keeps every agent in its lane: no writing outside its assigned paths, no approving its own work.

04One CLI for the everyday, Git underneath.

Committing, submitting, landing and snapshotting are runko commands in every checkout, so humans and agents learn one small set of verbs. Underneath it is ordinary Git — clone it, script it, keep your tools. When you need surgery on the middle of a stack, Jujutsu is first-class alongside it.

Why this growsThe constraint is moving, and it is not going back.

We are not betting that people will dislike GitHub. We are betting on a change in what the work looks like — and that the tools built for the old shape cannot stretch to the new one.

  • Change volume is decoupling from headcount.

    For thirty years the number of changes a company produced tracked the number of engineers it employed, and every tool in the stack was sized for that ratio. Agents break the link: the same team now opens several times the changes. Review queues, CI budgets and merge policies were all built against the old ratio, and they fail in that order.

  • When machines write the code, the gate has to be machine-checkable.

    You cannot scale "a senior engineer reads every diff" to agent volume. What does scale is enforcement the server can apply on its own: who owns this path, what does this change affect, which checks must be green, what is this identity allowed to touch. Runko puts exactly those things in the tree where they are versioned, reviewable, and cheap to evaluate.

  • Agents push teams toward monorepos.

    Splitting a codebase into many repos was, in part, a way to fit each piece into a human head and a human's checkout. Agents do not have that limit — but they are genuinely bad at coordinating across boundaries they cannot see. The cheapest fix is to remove the boundary, which makes monorepo tooling a requirement rather than a Google-scale luxury.

  • Adoption does not require a migration.

    Runko mirrors to any Git host, so a team can run it and keep GitHub as the place their code appears — issues, existing integrations and muscle memory intact. The front door is a mirror, not a cutover, which is how infrastructure like this actually spreads.

  • Open source and self-hosted, so trusting it is cheap.

    Your source code is the most sensitive asset you have, and the platform that governs it is the last place anyone wants a black box or a vendor lock. Runko is Apache-2.0 and runs on your own infrastructure. The substrate is plain Git, so the exit is always a git clone.

  • It is already carrying its own weight.

    Runko is developed on Runko. Every change to this platform is authored in a workspace, reviewed as a Change, gated by ownership and affected-scoped checks, and landed by the same engine you would be running — much of it by agents. The features exist because building this way surfaced the need for them.
